# Этап 0 — первичные сценарии

> MVP v1 scope update: этот Stage 0 документ сохраняется как historical traceability. Актуальный MVP v1 реализует hotel search; flight search и combined hotel+flight являются future expansion.

## Цель документа

Зафиксировать основные пользовательские сценарии верхнего уровня. Это не user stories, не функциональная спецификация и не критерии приемки MVP.

## 1. Подбор отеля по естественному запросу

Пользователь описывает желаемое проживание обычным языком: город, район, даты, бюджет, состав гостей, желаемую атмосферу, требования к удобствам, близость к точкам интереса или ограничения.

Ассистент должен на верхнем уровне:

- понять, что пользователь ищет отель;
- выделить известные параметры;
- определить, каких параметров не хватает;
- задать уточняющий вопрос при необходимости;
- подобрать варианты через будущего абстрактного провайдера отелей;
- объяснить, почему варианты соответствуют запросу.

## 2. Подбор авиабилета по естественному запросу

Пользователь описывает перелет: откуда и куда летит, примерные или точные даты, бюджет, багаж, желаемое время, допустимость пересадок и гибкость.

Ассистент должен на верхнем уровне:

- понять, что пользователь ищет перелет;
- выделить маршрут, даты и ограничения;
- уточнить критичные недостающие параметры;
- подобрать варианты через будущего абстрактного провайдера перелетов;
- объяснить trade-off между ценой, временем, пересадками и удобством.

## 3. Комбинированный подбор поездки: перелет + отель

Пользователь формулирует запрос на поездку целиком: куда хочет поехать, когда, с каким бюджетом, каким стилем отдыха и какими ограничениями.

Ассистент должен:

- разделить запрос на параметры перелета и проживания;
- выявить общие ограничения поездки;
- уточнить приоритеты, если бюджет, даты или комфорт конфликтуют;
- подобрать совместимые варианты перелета и отеля;
- объяснить, какие комбинации лучше соответствуют целям пользователя.

## 4. Уточнение требований ассистентом

Если запрос неполный, ассистент должен задавать уточняющие вопросы вместо того, чтобы строить рекомендации на случайных допущениях.

Типовые области уточнения:

- направление;
- город отправления;
- даты или гибкость дат;
- количество путешественников;
- бюджет;
- требования к отелю;
- ограничения по пересадкам, времени вылета, багажу;
- приоритет между ценой, комфортом, локацией и временем.

## 5. Сравнение нескольких вариантов

Пользователь может попросить сравнить найденные варианты. Сравнение должно показывать не только отличия, но и смысловые trade-off.

Возможные критерии сравнения:

- цена;
- длительность и удобство перелета;
- количество пересадок;
- локация отеля;
- рейтинг, удобства и тип размещения;
- соответствие бюджету;
- соответствие предпочтениям пользователя;
- риски и неопределенности.

## 6. Объяснение, почему вариант подходит

Ассистент должен объяснять рекомендации понятным языком. Пользователь должен видеть связь между своим запросом и предложенным вариантом.

Объяснение должно опираться на:

- явно указанные требования;
- выявленные предпочтения;
- параметры варианта;
- компромиссы;
- ограничения, которые не удалось полностью удовлетворить.

## 7. Сохранение или возвращение к найденным вариантам

Пользователь может захотеть вернуться к найденным вариантам, сравнить их позже или изменить часть требований.

На Этапе 0 это фиксируется как важный пользовательский сценарий. Механика хранения, авторизация, личный кабинет и долгосрочная история должны быть уточнены позже.

## 8. Работа с неполным, расплывчатым или противоречивым запросом

Пользователь может дать запрос без точных дат, бюджета или направления, либо указать конфликтующие требования.

Ассистент должен:

- выявлять неопределенность;
- отделять обязательные требования от пожеланий;
- называть противоречия;
- задавать уточняющие вопросы;
- предлагать возможные трактовки;
- не выдавать ложную уверенность.

## Не входит в Этап 0

- детализация user stories;
- описание всех edge cases;
- API-endpoint-ы;
- UI flows;
- доменная модель;
- алгоритм ранжирования;
- формат хранения найденных вариантов.
