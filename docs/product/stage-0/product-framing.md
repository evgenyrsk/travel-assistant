# Этап 0 — продуктовая рамка

> MVP v1 scope update: этот Stage 0 документ сохраняется как historical traceability. Актуальный MVP v1 ограничен hotel search; flight search и combined hotel+flight являются future expansion.

## Цель документа

Зафиксировать исходную постановку Travel Assistant на уровне продукта: что создается, для кого, какую пользовательскую ценность несет и какие границы важно сохранить до следующих этапов.

Этот документ не проектирует техническую архитектуру, не выбирает окончательный стек, не задает API-контракты и не является разрешением начинать реализацию.

## Что такое Travel Assistant

Travel Assistant — это AI-помощник для выбора отелей и авиабилетов по естественному пользовательскому запросу. Он должен помогать пользователю перейти от неструктурированной идеи поездки к понятному набору подходящих вариантов, уточняя недостающие параметры, учитывая предпочтения и объясняя рекомендации.

В перспективе Travel Assistant должен быть кроссплатформенным продуктом: пользовательский сценарий может начинаться в web, продолжаться в мобильном приложении iOS/Android или другом интерфейсе, а продуктовая логика должна оставаться общей.

## Какую проблему он решает

Обычный поиск отелей и авиабилетов требует, чтобы пользователь заранее знал точные параметры: направление, даты, бюджет, район, количество гостей, допустимые пересадки, багаж, класс обслуживания и другие фильтры. В реальности запрос часто начинается иначе: "хочу недорого на море в июле", "нужно удобно с ребенком", "важно не прилетать ночью", "хочу отель ближе к центру, но без переплаты".

Travel Assistant решает проблему перевода таких естественных, неполных или противоречивых запросов в осмысленный процесс выбора. Он должен помогать:

- выявлять намерение пользователя;
- уточнять критичные параметры;
- учитывать предпочтения и ограничения;
- находить подходящие варианты;
- объяснять trade-off между ценой, комфортом, временем, локацией и другими факторами;
- возвращаться к найденным вариантам и продолжать сравнение.

## Для кого создается продукт

Первичная аудитория на уровне Этапа 0:

- путешественники, которым сложно быстро выбрать отель или перелет среди большого числа вариантов;
- пользователи с предпочтениями, которые плохо описываются стандартными фильтрами;
- пары, семьи и небольшие группы с разными требованиями к поездке;
- пользователи, которые не знают точных параметров заранее и готовы уточнять их в диалоге;
- частые путешественники, которым в будущем может быть полезно повторное использование предпочтений.

Приоритетные сегменты пользователей должны быть уточнены на следующих этапах.

## Чем отличается от обычного поиска отелей и авиабилетов

Обычный поиск строится вокруг формы и фильтров. Travel Assistant должен строиться вокруг диалога и понимания смысла запроса.

Ключевые отличия:

- старт с естественного языка, а не с полной формы;
- уточнение недостающих параметров вместо молчаливых допущений;
- объяснение причин рекомендации;
- сравнение вариантов по trade-off, а не только по цене или рейтингу;
- поддержка комбинированного сценария "перелет + отель";
- возможность развивать сценарий через несколько платформ и интерфейсов.

## Роль AI/LLM

AI/LLM играет ключевую роль в пользовательском опыте, но не должен подменять все продуктовые и бизнес-правила.

Ожидаемые роли AI/LLM:

- понимать естественный запрос пользователя;
- извлекать намерения и параметры поездки;
- определять недостающие, расплывчатые или противоречивые требования;
- формулировать уточняющие вопросы;
- помогать ранжировать и объяснять рекомендации;
- поддерживать сравнение вариантов в диалоге.

На Этапе 0 не принимается решение о конкретном LLM-провайдере. В дальнейшем взаимодействие с LLM должно быть отделено от доменной логики через заменяемую абстракцию.

## Роль внутренних API организации

В будущем внутренние API организации могут использоваться для получения реальных офферов по отелям и авиабилетам. На текущих этапах интеграция с реальным API не нужна.

На Этапе 0 внутренние API рассматриваются как будущие источники-провайдеры за абстракциями. Это означает:

- не фиксировать внутренние DTO конкретного провайдера как продуктовую модель;
- не хардкодить особенности будущих API;
- использовать mock/fake providers и contract placeholders на ранних этапах до предоставления API-контракта;
- проектировать будущие интерфейсы так, чтобы реальные источники можно было подключить позже.

## Почему важна кроссплатформенность

Планирование поездки часто происходит не в одном сеансе и не на одном устройстве. Пользователь может начать запрос на web, продолжить сравнение на телефоне, вернуться к найденным вариантам позже или использовать другой интерфейс.

Поэтому уже на уровне постановки важно:

- описывать сценарии независимо от конкретного UI;
- не связывать продуктовую логику с одной платформой;
- закладывать возможность будущего web, мобильных приложений iOS/Android и других интерфейсов;
- отделять пользовательский сценарий от технических деталей конкретного клиента.

## Границы Этапа 0

Этап 0 фиксирует исходный контекст, цели, пользовательскую ценность, предварительные границы MVP, принципы разработки и открытые вопросы.

Этап 0 не включает:

- детальную архитектуру;
- выбор окончательного технического стека;
- API-контракты;
- схема базы данных;
- UI-дизайн или реализацию UI;
- backend/frontend skeleton;
- реальные интеграции с travel API или LLM;
- mock-сервер.
