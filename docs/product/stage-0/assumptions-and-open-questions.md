# Этап 0 — допущения и открытые вопросы

## Цель документа

Собрать рабочие допущения, принципы разработки, риски и вопросы, которые нужно решить позже. На Этапе 0 эти вопросы фиксируются, но не закрываются техническими решениями.

## Рабочие допущения

- Пользователь может начинать с неполного, расплывчатого или противоречивого запроса.
- AI/LLM нужен для понимания запроса, уточнений, объяснений и сравнения вариантов.
- Поиск отелей и авиабилетов в будущем должен идти через абстракции провайдеров.
- Внутренние API организации пока рассматриваются как внешние источники-провайдеры за абстракциями.
- На ранних этапах допустимы mock/fake providers и contract placeholders до предоставления API-контракта существующего travel API.
- Web может быть первой платформой, но продукт должен сохранять кроссплатформенную траекторию.
- Детальная архитектура, API-контракты, схема базы данных и UI не проектируются на Этапе 0.

## Принципы разработки проекта

- Идти поэтапно.
- Не перескакивать к реализации раньше времени.
- Каждый этап должен иметь понятный результат.
- Архитектура должна вытекать из требований, а не наоборот.
- Решения должны фиксироваться в документации.
- Спорные архитектурные решения фиксировать через ADR.
- Не раздувать границы задачи без необходимости.
- Сохранять возможность заменить технические детали позже.
- Внутренние API пока считать внешними провайдерами за абстракциями.
- Идеи для следующих этапов фиксировать как рекомендации, но не выполнять в рамках Этапа 0.

## Открытые вопросы

- Какие типы пользователей являются приоритетными для MVP?
- Что считать успешной рекомендацией?
- Нужно ли начинать только с отелей или сразу поддерживать перелеты тоже?
- Должен ли первый MVP поддерживать комбинированный сценарий "перелет + отель"?
- Какая первая платформа: сначала web или сначала mobile?
- Какой уровень персонализации нужен в MVP?
- Какие ограничения есть у внутренних API организации?
- Нужна ли авторизация в ранней версии?
- Как хранить предпочтения пользователя?
- Как пользователь должен возвращаться к найденным вариантам?
- Как объяснять рекомендации так, чтобы они были понятны и проверяемы?
- Как обрабатывать ошибки провайдеров?
- Как обрабатывать отсутствие подходящих офферов?
- Какие параметры обязательны перед началом поиска?
- Как показывать неопределенность, если запрос неполный?
- Какой уровень AI-автономности допустим в сценариях с ценами и доступностью?

## Риски

- Преждевременно перейти к технической архитектуре до требований.
- Слишком рано привязаться к API конкретного провайдера.
- Раздуть MVP до бронирования, платежей, личного кабинета и мобильных приложений.
- Смешать продуктовую логику с деталями первого web-интерфейса.
- Считать mock/fake данные финальной моделью предметной области.

## Рекомендации

- Следующий рекомендуемый шаг: Этап 1 — бизнес-требования.
- Не выполнять Этап 1 в рамках Этапа 0.
- На Этапе 1 уточнить приоритетные пользовательские сегменты, критерии успешной рекомендации и минимальные бизнес-требования.
