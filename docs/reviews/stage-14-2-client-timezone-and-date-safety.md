# Stage 14.2 — часовой пояс клиента и безопасность дат

## Цель

Закрыть критическую ошибку, при которой LLM мог подставить прошедший год для
относительной или не содержащей год даты, и согласовать поведение assistant
flow с двумя продуктовыми правилами:

- неуказанное количество номеров означает один номер;
- «сегодня/завтра» интерпретируются только относительно локальной даты
  пользователя либо требуют явного уточнения.

Этап также устраняет ложный абзац в assistant bubble, обнаруженный в том же
ручном сценарии.

## Причины наблюдаемого поведения

| Наблюдение | Причина |
|---|---|
| В confirmation мог появиться `2025`, хотя backend работает в `2026` | LLM-запрос не содержал текущей reference date, а backend не проверял извлечённую дату относительно текущего дня |
| Неуказанный номер считался недостающим полем | `rooms` не имел согласованного assistant-default |
| Первая строка assistant bubble выглядела как отдельный абзац | `white-space: pre-wrap` сохранял отступ исходного многострочного HTML |
| Реплика с завтраком могла не пройти безопасное преобразование полностью | Завтрак не входит в четыре поддерживаемых предпочтения; точный внутренний результат LLM намеренно не раскрывается и не сохраняется |

## Правила интерпретации дат

Demo shell передаёт на каждом сообщении необязательные `locale` и IANA
`timezone`, полученные из браузера. Backend использует только timezone:

1. текущий instant берётся из backend-owned `Clock`;
2. timezone преобразует этот instant в локальную `referenceDate`;
3. `referenceDate` передаётся во внутренний запрос LLM;
4. LLM обязан разрешать относительные даты и выбирать ближайший не прошедший
   год для даты без года;
5. application layer повторно отклоняет дату заезда в прошлом и дату выезда,
   которая не позже текущей допустимой даты.

Клиентский timestamp не принимается и не считается источником истины. Если
timezone отсутствует или некорректен, относительные и не содержащие год даты
удаляются из candidate, а пользователь получает просьбу указать день, месяц и
год. Для явно указанной абсолютной даты timezone не обязательна.

При отсутствии timezone application layer использует дату в `UTC-12` только
как консервативную нижнюю границу для отбрасывания однозначно прошедших дат. Эта
граница не используется для интерпретации «сегодня/завтра».

## Номер по умолчанию

Новый `AssistantHotelConstraints` начинается с `rooms=1`. Явно переданное
значение по-прежнему валидируется. Legacy strict handoff использует тот же
default, а диагностический `POST /hotel-searches` не изменён. Confirmation
показывает один номер, даже если пользователь не называл его в сообщении.

## Изменения

Production:

- чтение контекста браузера и его передача через существующий
  `AssistantMessageRequest.clientContext`;
- типизированный `ZoneId` внутри backend-команды без переноса timezone в domain;
- `referenceDate` во внутреннем `LlmCandidateRequest` и OpenRouter prompt;
- принадлежащая application-слою `AssistantDateInterpretationPolicy`;
- повторная проверка новых и накопленных дат до confirmation/search;
- default одного номера;
- нормализация текста bubble без изменения его содержимого.

Активная документация и OpenAPI draft согласованы с фактическим поведением.
Public request/response shape, routes и provider contracts не расширялись:
`clientContext.locale/timezone` уже существовал в контракте.

## Тестовое покрытие

- локальная дата `Europe/Moscow` вычисляется из фиксированного backend instant;
- относительные даты без timezone и с некорректной timezone требуют явного
  дня, месяца и года;
- ошибочно извлечённые даты `2025` отклоняются при текущем `2026`;
- ранее накопленные даты повторно проверяются при следующем сообщении;
- неуказанное количество номеров становится равным одному;
- timezone браузера передаётся и в первое, и в последующие сообщения;
- отсутствие подсказок браузера не приводит к выдуманным значениям;
- исходные и динамические assistant messages не сохраняют лишние внешние
  пробелы.

## Границы

- live OpenRouter и Hotels API вызовы не выполняются;
- `locale` пока не меняет поведение;
- timezone не сохраняется в process-local session store и передаётся на каждом
  сообщении;
- breakfast/meal preference, новые filters, provider calls, auth, durable
  storage и deployment не добавлены;
- OpenAPI и generated clients сохраняют `not_ready`.

## Оставшийся вопрос

Фраза «чтобы были завтраки» пока является неподдерживаемым предпочтением. Без
подтверждённого значения фильтра Hotels API ассистент не должен молча обещать или
игнорировать это условие. Безопасный следующий кандидат — отдельная проверка
контракта фильтра питания/завтрака и только затем расширение модели предпочтений.

## Verdict

`COMPLETED_CRITICAL_DATE_SAFETY`.

Stage 14.2 закрывает ошибку года, неоднозначность относительных дат и номер по умолчанию в
assistant flow. Это не закрывает live image evidence Stage 14.1c и не означает
production readiness.
