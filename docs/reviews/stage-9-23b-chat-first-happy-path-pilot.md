# Stage 9.23b — сквозная проверка успешного chat-first сценария

## Роль документа

Это отчет об одной контролируемой проверке успешного сценария внутреннего
пилота. Текущий статус проекта задает
[`docs/roadmap/roadmap.md`](../roadmap/roadmap.md).

## Цель

После усиления семантического контракта Stage 9.23a один раз проверить полный
путь:

`chat-first UI → OpenRouter → confirmation → REAL Hotels → карточки`.

Проверка не закрывает весь Stage 9.23 и не означает готовность к промышленному
использованию.

## Условия

- дата проверки: 19 июля 2026 года;
- локальный frontend: `http://127.0.0.1:4173`;
- локальный backend: `http://127.0.0.1:8080`;
- LLM mode: явно включенный `OPENROUTER`;
- Hotels mode: локальное для процесса переопределение `REAL`;
- оба режима по умолчанию в проекте остались `FAKE`;
- использован синтетический запрос на отель в Казани для двух взрослых без
  детей и одной комнаты на 10–14 августа 2026 года.

Ключи, headers, cookies, сырые ответы OpenRouter и Hotels API не сохранялись и
не выводились.

## Результат

| Шаг | Результат |
|---|---|
| Первый пользовательский запрос | Assistant session создана, параметры распознаны |
| Confirmation boundary | Показан вопрос «Проверить отели по этим параметрам?» |
| До подтверждения | `hotelSearchId` отсутствовал, карточки не загружались |
| Явное подтверждение | Отправлено отдельным сообщением «Да» |
| REAL Hotels | Поиск завершен успешно, создан `hotelSearchId` |
| Candidate pool | Backend вернул 20 предложений |
| Представление | Frontend показал 5 лучших карточек |
| Ошибки браузера | Не обнаружены |

Браузер обращался только к локальным `/api/v1/**`: создание Assistant session,
отправка подтверждения и получение offers по созданному `hotelSearchId`.
OpenRouter и Hotels API не вызывались напрямую из браузера.

## Подтвержденные границы

- поиск не начался до явного подтверждения;
- успешный LLM candidate прошел application validation;
- `hotelSearchId` появился только после подтвержденного поиска;
- presentation layer ограничил пул из 20 предложений пятью карточками;
- цена, валюта, availability и guest rating отображались как provider facts;
- дополнительных пользовательских сообщений, повторных pilot-сценариев и
  автоматической смены модели не выполнялось;
- `.env`, provider configuration, runtime defaults и production code не
  изменялись.

## Наблюдения для стабилизации

Проверка выявила два некритичных вопроса пользовательского качества:

- финальное сообщение ассистента и `matchSummary` отображаются на английском;
- одно из предложений имело подозрительно короткое отображаемое имя из двух
  символов и требует отдельной проверки качества provider data/mapping.

Также frontend запросил отсутствующий `favicon.ico` и получил `404`. Это не
повлияло на сценарий.

Эти наблюдения не исправлялись в рамках live-проверки и не считаются
Critical/Major дефектами подтвержденного happy path.

## Что осталось проверить

Stage 9.23 остается в работе. До его закрытия нужна ограниченная pilot-матрица:

- уточнение отсутствующих дат без потери destination;
- запрос возраста явно указанного ребенка;
- неоднозначная location без автоматического выбора;
- отказ от confirmation без вызова Hotels API;
- безопасная граница для flight/booking request;
- безопасные outcomes при отказе OpenRouter и Hotels API;
- отображение неизвестных rating/amenities без выдуманных значений;
- сохранение provider price и currency без пересчета.

Отказы провайдеров следует проверять детерминированно через существующие test
seams. Новые live-вызовы допустимы только там, где они действительно нужны, и
после отдельного разрешения.

## Verdict

`PASS_HAPPY_PATH_STAGE_9_23_REMAINS_IN_PROGRESS`.

Stage 9.23b подтверждает первый сквозной пользовательский сценарий. Следующий
безопасный шаг — Stage 9.23c: ограниченная проверка оставшейся pilot-матрицы и
классификация найденных дефектов без расширения hotel-only MVP.
