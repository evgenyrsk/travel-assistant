# Stage 14.5 — явное уточнение звёзд и диагностика источника изображений

## Цель

Закрыть воспроизведённый случай, когда явно сформулированное требование
пятизвёздочного отеля не попадало в повторное confirmation, и определить,
почему REAL-карточки остаются без фотографий.

## Результат диагностики

- Обе пользовательские реплики получили `CANDIDATE_DECODED`: transport,
  декодирование структурированного ответа и общая валидация candidate
  отработали успешно.
- Во втором candidate поле `stars` осталось пустым, поэтому в накопленных
  preferences сохранился только ранее установленный завтрак.
- Текущий public offers response не содержал `imageUrl`; в DOM пяти карточек
  отсутствовали элементы `img` и отображался предусмотренный fallback.
- На этом этапе raw provider response не проверялся повторно, поэтому источник
  image facts оставался неизвестным.

Следовательно, уточнение звёзд было семантическим пропуском LLM. Точная причина
отсутствия фотографий была установлена следующим Stage 14.6: provider вернул
image templates с `{size}`, которые отклонялись до разрешения placeholder.

## Изменения

- Добавлен application-owned `ExplicitHotelStarPreferenceParser`.
- Parser распознаёт только точную одиночную категорию `1..5` в явных
  формулировках, включая `пятизвёздочный`, `пятизвездочный`, `5 звёзд` и
  `пять звёзд`.
- Unicode, регистр, пробелы и `ё/е` нормализуются детерминированно.
- Диапазоны, сравнения, отрицания и команды снятия ограничения parser не
  интерпретирует: они остаются ответственностью LLM и сценария уточнения.
- Явно распознанная категория дополняет LLM preference patch и удаляет только
  конфликтующий `clear(stars)`; остальные извлечённые поля не меняются.
- Добавлено безопасное событие `PREFERENCE_STARS_ENRICHED`. Лог содержит только
  фиксированную категорию и не содержит сообщения, prompt, identifiers или
  provider data.
- OpenRouter prompt получил точные русские примеры для категории `5`.

## Граница изображений

На момент Stage 14.5 публичные offers не содержали готового `imageUrl`, поэтому
frontend корректно показывал нейтральный placeholder. Stage 14.6 уточнил, что
отдельный пакетный источник не требуется: основной search уже возвращает
image templates.

В этап намеренно не добавлены:

- пять автоматических details-запросов для пяти карточек;
- N+1 или скрытая фоновая загрузка;
- вычисление image URL из provider ID;
- сторонние или выдуманные фотографии;
- неподтверждённый web endpoint `getHotelStaticInfo`.

Разрешение template и его проверки выполнены отдельным Stage 14.6.

## Проверки

- parser распознаёт точную пятизвёздочную формулировку;
- числовая и словесная формы дают категорию `5`;
- диапазоны, сравнения, снятие ограничения и отрицания не превращаются в
  точный фильтр;
- сквозная проверка уточнения с пустым LLM `stars` сохраняет завтрак, добавляет
  `5 звёзд`, не создаёт новый `hotelSearchId` до подтверждения и записывает
  только безопасное диагностическое событие;
- prompt contract содержит явный русский пример;
- существующие mapping preferences и жизненный цикл подтверждения не меняются.

## Границы

- public API, OpenAPI и demo frontend не меняются;
- provider search, details и ranking не меняются;
- новый provider endpoint и live probe не добавляются;
- `FAKE` остаётся default, stores остаются process-local;
- результат не является production readiness.

## Verdict

`IMPLEMENTED_AND_LOCALLY_VERIFIED` после прохождения обязательных backend
gates.

Stage 14.5 закрывает семантический пропуск для точной категории звёзд.
Исторический вывод об изображениях уточнён Stage 14.6, который подтвердил и
исправил template contract без изменения CSS.
