# Stage 12.7 — уточнение поиска при пустой выдаче

## Цель

Безопасно отличить успешный поиск без предложений от ошибки provider и
предложить пользователю одно понятное ослабление активных условий. Никакое
условие не меняется без новой реплики пользователя и повторного подтверждения.

## Разделение результатов

- `COMPLETED_NO_OFFERS` означает, что provider search выполнен успешно, поэтому
  поиск сохраняется и остаётся доступен по своему `hotelSearchId`.
- Ошибка request mapping, provider response или доступности provider остаётся
  `NotCreated`: поиск и `hotelSearchId` не создаются.
- Успешный пустой результат не маскируется как provider failure, а provider
  failure не превращается в пустой список.

## Application policy

Добавлены `PlanHotelNoOffersRefinementUseCase` и typed
`HotelNoOffersRefinementPlan`. Policy применяется только к сохранённому
`COMPLETED_NO_OFFERS` с пустым списком предложений и работает без mutation,
provider calls и доступа к transport.

Если активно несколько условий, выбирается ровно одно в фиксированном порядке:

| Порядок | Условие | Причина |
|---:|---|---|
| 1 | минимальный гостевой рейтинг | сначала ослабляется субъективное quality-условие |
| 2 | звёзды | затем категория объекта размещения |
| 3 | бесплатная отмена | защитное условие снимается после quality-условий |
| 4 | максимальная общая стоимость | финансовое ограничение предлагается снять последним |

Если активных предпочтений нет, backend не придумывает рекомендацию. Изменение
destination, дат или состава гостей остаётся обычной следующей репликой в чате.

## Публичный ответ и demo shell

Существующий `GET /api/v1/hotel-searches/{searchId}/offers` может вернуть
необязательный `refinementSuggestion`:

- `type=relax_preference`;
- provider-neutral имя одного preference;
- безопасный пользовательский текст.

Поле отсутствует для выдачи с предложениями и для пустого поиска без активных
preferences. OpenAPI запрещает неизвестные поля и ограничивает значения
четырьмя текущими preference. Общий статус OpenAPI остаётся `not_ready`.

Demo shell показывает рекомендацию как следующую реплику ассистента. Она не
отправляет сообщение автоматически, не меняет session context и не запускает
новый поиск. Пользователь может принять, изменить или проигнорировать совет;
действующий Stage 12.5 flow снова показывает полный confirmation prompt.

Текст готовности результата сделан нейтральным: успешный поиск больше не
утверждает, что подходящие варианты обязательно существуют до чтения offers.

## Проверки

- policy не применяется к непустой выдаче или отсутствующим preferences;
- детерминированный порядок покрыт unit tests;
- планирование не изменяет сохранённые критерии;
- API возвращает один typed suggestion для пустого сохранённого поиска;
- demo shell отображает suggestion без дополнительного API-вызова;
- OpenAPI conformance проверяет optionality, закрытую schema и допустимые enum;
- provider failure по-прежнему не раскрывает внутренние причины и не создаёт
  `hotelSearchId`.

## Вне этапа

Не добавлены автоматическое ослабление, вызов `search-filters-availability`,
повторный provider request, pagination, пользовательская сортировка, filter
panel, auth, durable storage, SDK, booking или payment. Live-вызовы не
выполнялись.

## Следующий этап

Stage 12.8 — итоговая проверка iterative-refinement MVP: полный regression,
сценарии установки/снятия условий, пустая выдача, safe failures и один отдельно
разрешённый REAL smoke без автоматического повтора.

## Verdict

`PASS_STAGE_12_7_NO_RESULTS_REFINEMENT`.

Пустой успешный search и provider failure имеют разные lifecycle-результаты, а
ослабление условий остаётся явным пользовательским решением с новым
подтверждением.
