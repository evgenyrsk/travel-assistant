# Stage 12.2 — provider-neutral модель предпочтений поиска

## Цель

Добавить внутреннюю модель четырех подтвержденных предпочтений и безопасное
накопление изменений по `AssistantSessionId`. Этап не извлекает предпочтения
через LLM, не преобразует их в Hotels API filters и не меняет runtime flow.

## Что добавлено

`HotelSearchPreferences` хранит только бизнес-смысл:

| Поле | Политика первого среза |
|---|---|
| `maxTotalPrice` | Положительная общая стоимость за весь период; отсутствие валюты означает `RUB`, другие валюты пока отклоняются без конвертации |
| `stars` | Непустой набор значений `0..5`; порядок не влияет на смысл |
| `minimumGuestRating` | Только дискретные пороги `5`, `6`, `7`, `8`, `9` |
| `freeCancellationRequired` | `true` означает обязательную бесплатную отмену; снятие выполняется через `CLEAR` |

Модель не содержит `filterId`, `$objectType`, transport DTO или других
Hotels API деталей. Пустое значение по умолчанию сохраняет прежний поиск без
фильтров.

## Patch и накопление

`HotelSearchPreferencePatch` задает три операции:

- `KEEP` — сохранить текущее значение;
- `SET` — установить или заменить явно переданное значение;
- `CLEAR` — снять ограничение.

`ApplyHotelSearchPreferencesPatchUseCase` использует существующий
`AssistantHotelConstraintsStore`, поэтому обязательные критерии и preferences
остаются одним привязанным к session контекстом поиска. Patch применяется атомарно:
наличие любой ошибки проверки сохраняет весь предыдущий набор без частичного
обновления.

Проверяются положительная стоимость, текущая валюта `RUB`, диапазон звезд,
дискретный порог рейтинга и каноническое включение бесплатной отмены.
Process-local хранение остается допустимой границей локального MVP.

## Confirmation и idempotency

Активные preferences добавляются к confirmation proposal в стабильном порядке.
Неактивные поля не показываются. Стоимость явно подписывается как общая за весь
период.

`ConfirmedSearchExecutionIdempotencyKey` теперь учитывает:

- нормализованные amount и currency;
- отсортированный набор звезд;
- дискретный порог рейтинга;
- требование бесплатной отмены.

Эквивалентный порядок звезд и разные равнозначные записи цены дают одинаковую основу,
а изменение любого preference — другую поисковую попытку.

## Проверки

Точечные тесты покрывают:

- единый patch с четырьмя preferences;
- `KEEP`, `SET` и `CLEAR`;
- атомарный отказ без частичного изменения состояния;
- границы звезд `0..5` и рейтинга `5..9`;
- изоляцию session state и сохранение обязательных критериев;
- поля confirmation и перенос preferences в `HotelSearchCriteria`;
- детерминированную основу idempotency.

Выполнены и прошли:

- точечные тесты новых preferences, confirmation, mapper и idempotency;
- полный `services/backend` test suite;
- `git diff --check`;
- проверка границ diff и отсутствия route, API, OpenAPI, frontend и provider
  integration changes.

## Границы этапа

Stage 12.2 не добавляет:

- LLM extraction или новые structured-output поля;
- provider filter DTO и mapping;
- вызовы Hotels API, pagination или повторный поиск;
- route/runtime wiring;
- public API, OpenAPI или frontend changes;
- пользовательскую сортировку, auth или durable storage.

## Следующий этап

Stage 12.3 должен преобразовывать явные пользовательские формулировки в typed
patch, поддерживать снятие ограничений и запрашивать уточнение для
неподдерживаемых значений. Он не должен отправлять provider request до нового
подтверждения.

## Verdict

`PASS_STAGE_12_2_PROVIDER_NEUTRAL_PREFERENCE_MODEL`.

Внутренняя модель и безопасная session-bound основа готовы. Реальное извлечение
из диалога и Hotels API mapping остаются отдельными этапами.
