# Stage 9.21c — ограниченная политика повторов OpenRouter

## Роль документа

Это отчет о реализации Stage 9.21c. Он фиксирует внутреннюю политику одного
дополнительного LLM-вызова после безопасно классифицированного временного отказа.
Текущий статус проекта задает
[`docs/roadmap/roadmap.md`](../roadmap/roadmap.md).

## Цель

Снизить вероятность случайного отказа OpenRouter без неограниченных повторов,
смены модели и изменения публичного поведения assistant. Один запрос
пользователя может привести не более чем к двум одинаковым LLM-запросам.

## Реализация

Прикладной слой владеет:

- `LlmClientResponse.RetryableFailure` с причиной, независимой от provider;
- `LlmCandidateRetryPolicy` с вариантами `NO_RETRY` и `SINGLE_RETRY`;
- общим счетчиком попыток в `GenerateLlmCandidateUseCase`.

Infrastructure-адаптер только переводит безопасную категорию OpenRouter в
результат с возможностью или без возможности повтора. Сам
`OpenRouterLlmClient` не выполняет повтор. Поэтому вложенные политики не могут
увеличить лимит до четырех запросов.

`LlmProviderRuntime` передает `SINGLE_RETRY` только для режима `OPENROUTER`.
Режим `FAKE` и прямые тестовые точки внедрения по умолчанию используют
`NO_RETRY`.

## Матрица решений

| Результат | Повтор |
|---|---|
| Тайм-аут, сетевая ошибка, недоступность provider | Один дополнительный вызов |
| Ошибка provider внутри успешного HTTP-ответа | Один дополнительный вызов |
| Некорректная JSON-оболочка | Один дополнительный вызов |
| Пустые `choices` или `content` | Один дополнительный вызов |
| Некорректный декодированный или проверенный candidate | Один дополнительный вызов |
| Некорректный request | Нет |
| Ошибка аутентификации, недостаток средств | Нет |
| Ограничение частоты `429` | Нет |
| Неизвестный HTTP status, non-JSON или неизвестный отказ | Нет |

Повтор использует тот же request и ту же конфигурацию модели. Задержка,
`Retry-After`, смена модели и автоматическая смена provider не добавлены.

## Cancellation и безопасный fallback

`CancellationException` пробрасывается с первой и второй попытки. Неожиданный
`RuntimeException`, не классифицированный client-ом, не допускает повтора и
переходит в существующий безопасный fallback.

После двух неуспешных результатов возвращается прежний typed validation
outcome. Public route не получает API key, model, raw body, diagnostic category
или внутреннюю причину.

## Проверки

Через fake-реализации и `MockEngine` подтверждены:

- временный отказ с последующим корректным candidate выполняет ровно два запроса;
- два временных отказа не создают третью попытку;
- пустой и некорректный candidate допускают только один повтор;
- `429` и остальные результаты без возможности повтора выполняют один запрос;
- `FAKE` сохраняет прежнее поведение без повторов;
- cancellation с первой или второй попытки пробрасывается;
- diagnostic observer сохраняет последовательность безопасных событий;
- confirmation response после успешной второй попытки не содержит
  `hotelSearchId`.

Точечные тесты, полный backend test suite и `git diff --check` пройдены. Live
QA в Stage 9.21c не выполнялся.

## Границы

Stage 9.21c не меняет:

- public API, OpenAPI, frontend или generated clients;
- Hotels API transport/runtime и hotel ranking;
- модель OpenRouter, prompt и structured schema;
- streaming, plugins, tools, web search или conversation storage;
- durable storage и production observability.

Ограниченный повтор уменьшает риск временного отказа, но не гарантирует
доступность внешнего provider и не означает production readiness.

## Verdict

`PASS_BOUNDED_OPENROUTER_RETRY_POLICY`.

Stage 9.21c завершен. Следующий разрешенный этап — Stage 9.22: основной
сценарий чата во frontend поверх существующих backend routes.
