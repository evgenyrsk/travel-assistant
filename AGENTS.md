# AGENTS.md

Этот репозиторий содержит Travel Assistant — AI-помощника для планирования путешествий. Продукт должен помогать пользователям описывать потребности поездки на естественном языке, уточнять недостающие параметры, искать перелеты и отели через абстрактные интерфейсы провайдеров, ранжировать предложения по предпочтениям пользователя и объяснять, почему вариант подходит.

## Предварительные технические ориентиры

Эти ориентиры описывают рабочие гипотезы и защитные архитектурные границы. Они не являются разрешением начинать реализацию, не подменяют этап формирования требований и не считаются финальной архитектурой без соответствующих roadmap-задач.

Технические ориентиры не являются активными implementation instructions. Не используй их как основание создавать код, модули, зависимости, skeleton, infrastructure, API contracts, DB schema, provider adapters или другие implementation artifacts, если активная roadmap-задача явно не разрешает такую работу.

- backend: Kotlin + Ktor как подтвержденный целевой stack Travel Assistant;
- frontend: Next.js + React + Tailwind + shadcn/ui как рабочая гипотеза;
- data: PostgreSQL как основное хранилище; Redis только при наличии подтвержденного сценария кэширования;
- AI: независимая от провайдера абстракция `LlmClient`;
- orchestration: начинать с простой собственной логики оркестрации, не вводя тяжелые агентные frameworks преждевременно;
- integrations: внешние travel API должны быть скрыты за интерфейсами провайдеров и начинаться как mock/stub провайдеры.

Перед технической реализацией должны быть последовательно уточнены требования, пользовательские сценарии, границы MVP, критерии приемки, доменная модель, архитектурные ограничения и конкретные roadmap-задачи.

Для Travel Assistant backend implementation должна использовать Kotlin + Ktor, если только будущий явный ADR и согласованная с roadmap задача не изменят backend stack. Java/Spring Boot не является принятым backend stack. Если существующие файлы реализации конфликтуют с этим правилом, Codex должен остановиться и сообщить об архитектурном расхождении вместо продолжения реализации.

## Границы контекста проекта

Источником истины является фактическое содержимое текущего репозитория и файлы, явно приложенные пользователем к текущей задаче. Перед ссылкой на файл или директорию убедись, что они существуют в текущем репозитории. Если пользователь или задача ссылается на несуществующий путь, не создавай его автоматически: найди ближайший существующий документ, работай только с ним, если это безопасно, и укажи расхождение в финальном отчете.

Не предполагается наличие `docs/product/`, `docs/architecture/stage-*`, `docs/product/stage-*` или `docs/decisions/`, если они не были явно созданы отдельной задачей в этом репозитории.

## Иерархия governance-документов

`AGENTS.md` является canonical source для глобальных правил работы Codex/AI-агентов в этом репозитории: scope control, roadmap control, documentation language, validation, diff discipline, безопасный workflow и обязательный формат финального отчета.

Остальные документы не должны конкурировать с `AGENTS.md`:

- `docs/prompts/**` — reusable prompt templates, task/review structures и prompt-writing guidance; они должны ссылаться на `AGENTS.md` для глобальных правил.
- `.github/**` — lightweight issue/PR templates для GitHub workflow; они не должны дублировать длинные Codex governance blocks.
- `README.md`, `docs/ROADMAP.md` и `docs/roadmap/roadmap.md` — navigation, project status и roadmap context; они не являются источником Codex execution rules.
- `docs/development/**` — future/reference material для будущей реализации; они не являются active backlog или agent governance source.
- `docs/reviews/**` — audit trail и cleanup reports; они не являются active task backlog.

Если пользователь ссылается на путь документа, которого нет, используй ближайший существующий документ репозитория и укажи это расхождение в финальном отчете.

## Обязательный рабочий процесс

Перед изменениями:

- определи текущий roadmap-этап по `docs/roadmap/roadmap.md`, если файл существует;
- проверь, относится ли задача к текущему этапу, явно активированной roadmap-задаче или безопасной documentation cleanup/refactoring работе;
- найди релевантные source-of-truth документы из списка обязательного чтения;
- перед backend implementation сверь backend stack с `docs/architecture/architecture-baseline.md`;
- проверь ADR в `docs/decisions/`, только если директория существует и ADR применимы к задаче;
- сформулируй минимальный scope изменений;
- определи ожидаемые файлы для изменения;
- только после этого вноси изменения.

После изменений:

- проверь diff на unrelated changes и случайное расширение scope;
- запусти релевантные проверки, если они доступны и не требуют придумывать новый tooling;
- не скрывай ошибки проверок;
- если проверка не запускалась или упала, укажи точную команду и причину;
- заверши ответ обязательным финальным отчетом.

## Контроль diff

- Предпочитай smallest meaningful diff, который решает текущую задачу.
- Не форматируй unrelated sections и не меняй структуру документа без необходимости.
- Не переименовывай файлы, разделы или термины, если это не требуется задачей.
- Не выполняй opportunistic refactoring и соседние улучшения.
- Сохраняй существующий стиль, терминологию, язык и структуру документов.
- Предпочитай обновлять существующие файлы вместо создания новых, если это безопасно и соответствует задаче.

## Проверки и валидация

- Для documentation-only задач запускай `git diff --check`, если команда доступна.
- Для новых или измененных ссылок вручную проверь, что они указывают на существующие файлы или явно создаются текущей задачей.
- Для backend/frontend задач сначала изучи существующие build/test scripts и только потом выбирай команды проверки.
- Не добавляй зависимости, scripts, configs или tooling только ради прохождения проверки.
- Не выдумывай команды проверки, которых нет в проекте или которые не следуют существующему tooling.
- Если проверку нельзя выполнить, объясни почему в разделе `Проверки`.
- Если проверка упала, укажи точную команду и краткую причину сбоя.

Если документы противоречат друг другу, не выбирай молча удобную версию. Следуй более приоритетному источнику, зафиксируй конфликт в разделе `Открытые вопросы` и не выполняй работу, которая может нарушить roadmap, границы задачи или ADR.

## Контроль roadmap

- Проект ведется поэтапно: сначала требования, пользовательские сценарии, границы MVP и критерии приемки; затем доменная модель и архитектурные ограничения; только после этого техническая реализация.
- Не переопределяй roadmap.
- Не меняй порядок этапов roadmap.
- Не начинай следующий этап roadmap без явного запроса пользователя.
- Не трактуй задачу как разрешение выполнять работу из будущих этапов.
- Работай только внутри явно указанного или очевидно текущего этапа roadmap.
- Перед изменениями определи текущий этап и проверь, что задача относится к нему.
- Не перескакивай к реализации, выбору библиотек, созданию backend/frontend skeleton, интеграциям или инфраструктуре, если текущая задача относится к продуктовой или аналитической проработке.
- Используй технические ориентиры только как контекст и защитные границы, а не как основание для расширения границ задачи.
- Не добавляй артефакты будущего этапа, даже если они кажутся маленькими или полезными.
- Не превращай подготовительную задачу в реализацию продукта.
- Не добавляй реальные интеграции с LLM/travel API, production-инфраструктуру или UI/backend skeleton, если текущий этап этого не требует.
- Если запрошено обновление roadmap, обновляй только подходящую существующую область roadmap и сохраняй порядок этапов.
- Если подходящей области roadmap нет, перечисли предлагаемую будущую работу в разделе `Рекомендации, не выполнены` финального отчета вместо реализации.

## Контроль границ задачи

- Держи каждое изменение маленьким, атомарным и соответствующим запрошенной задаче.
- Не расширяй границы задачи, если без этого можно выполнить текущую задачу.
- Не выполняй рекомендации в рамках той же задачи.
- Не исправляй соседние проблемы, если они не блокируют задачу.
- Не добавляй новые документы, директории, шаблоны, зависимости или tooling без явного запроса.
- Не создавай автоматически `docs/product/`, `docs/architecture/stage-*`, `docs/product/stage-*` или `docs/decisions/`.
- Если задача требует похожую структуру, сначала используй существующие документы текущего репозитория или укажи предложение в `Рекомендации, не выполнены`.
- Если обнаружена полезная будущая работа, запиши ее только в `Рекомендации, не выполнены`.
- Не добавляй реальные интеграции с travel API до стабилизации доменной модели и интерфейсов провайдеров.
- Не хардкодь детали внешних API, учетные данные или допущения, специфичные для провайдера.
- Не трогай unrelated files.

## Контроль ADR

- `docs/decisions/` используется только если эта директория реально существует в текущем репозитории.
- Не предполагается, что `docs/decisions/` существует.
- Если `docs/decisions/` отсутствует, не ссылайся на ADR как на обязательный источник.
- Перед изменением архитектуры, публичных контрактов, зависимостей, структуры модулей или интерфейсов провайдеров проверь ADR только при фактическом наличии `docs/decisions/`.
- Если ADR существуют в текущем репозитории, они имеют приоритет над общими заметками, README и неформальными комментариями.
- Не нарушай существующий ADR без явного запроса пользователя.
- Не создавай ADR автоматически.
- Если задача требует решения, которое не покрыто существующими ADR, укажи необходимость ADR в `Рекомендации, не выполнены`, если создание ADR не входит в текущую задачу.
- Если задача конфликтует с ADR, остановись на безопасной части работы, опиши конфликт в `Открытые вопросы` и не выполняй спорное изменение.

## Контроль архитектуры

- Держи доменную логику независимой от Ktor, Next.js, PostgreSQL, Redis и конкретных LLM-провайдеров.
- Держи Ktor routing тонким слоем и делегируй поведение в application/domain use cases.
- Держи LLM-оркестрацию независимой от провайдера через `LlmClient`.
- Держи travel search за интерфейсами провайдеров перелетов и отелей.
- Предпочитай mock/stub провайдеры, пока доменная модель MVP и контракты не стабилизированы.
- Не вводи Java/Spring Boot backend implementation в этом репозитории без явного запроса, принятого architecture decision / ADR и согласованной с roadmap задачи.
- Не используй historical stage artifacts как текущий источник backend stack, если существуют `docs/roadmap/roadmap.md` и `docs/architecture/architecture-baseline.md`.
- Если файлы реализации конфликтуют с подтвержденным backend stack Kotlin + Ktor, остановись и зафиксируй архитектурное расхождение в отчете.

## Контроль документации

- Public contracts и architecture decisions должны быть задокументированы до реализации или вместе с ней.
- Если меняется поведение, архитектура или рабочий процесс задачи, обнови релевантную документацию.
- README и индексные документы обновляй только когда меняется навигация, расположение важных файлов, способ запуска или основной рабочий процесс.
- Новая и обновленная документация должна сохранять русский как основной язык; английские technical terms, file paths, commands, API names и framework names можно оставлять без перевода.
- Не добавляй ссылки на несуществующие документы, если задача явно не создает эти документы.
- Не дублируй подробное содержание roadmap в README; README должен оставаться навигационным входом.
- Будущая работа должна фиксироваться только в разделе `Рекомендации, не выполнены`, а не реализовываться молча.
- ADR, если они есть, имеют приоритет над неформальными заметками.

## Конфликты и неопределённость

- Если задача, roadmap и ADR конфликтуют, соблюдай ADR и текущий roadmap, а конфликт вынеси в `Открытые вопросы`.
- Если пользователь явно просит нарушить roadmap или ADR, выполни только безопасную часть и уточни риск в финальном отчете.
- Если текущий этап не указан, выведи его из roadmap и затронутых файлов. Если это невозможно сделать уверенно, не начинай потенциально опасную реализацию.
- Если acceptance criteria неоднозначны, выбери минимальное изменение, которое соответствует задаче, и зафиксируй допущение в `Принятые решения`.
- Если непонятно, является ли изменение будущим этапом, считай его будущей работой и добавь только в `Рекомендации, не выполнены`.

## Обязательный формат финального отчета

Каждый ответ по задаче должен завершаться этими разделами:

1. Созданные файлы
2. Изменённые файлы
3. Краткое описание изменений
4. Проверки
5. Принятые решения
6. Открытые вопросы
7. Scope control
8. Рекомендации, не выполнены

Держи отчет кратким. Если в разделе нет пунктов, напиши `Нет`.
