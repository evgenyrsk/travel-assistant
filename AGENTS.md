# AGENTS.md

Этот репозиторий содержит Travel Assistant — AI-помощника для планирования путешествий. Продукт должен помогать пользователям описывать потребности поездки на естественном языке, уточнять недостающие параметры, искать перелеты и отели через абстрактные provider-интерфейсы, ранжировать предложения по предпочтениям пользователя и объяснять, почему вариант подходит.

## Предварительные технические ориентиры

Эти ориентиры описывают рабочие гипотезы и защитные архитектурные границы. Они не являются разрешением начинать реализацию, не подменяют этап формирования требований и не считаются финальной архитектурой без соответствующих roadmap-задач.

- backend: Kotlin + Ktor как рабочая гипотеза;
- frontend: Next.js + React + Tailwind + shadcn/ui как рабочая гипотеза;
- data: PostgreSQL как основное хранилище; Redis только при наличии подтвержденного сценария кэширования;
- AI: независимая от провайдера абстракция `LlmClient`;
- orchestration: начинать с простой собственной orchestration-логики, не вводя тяжелые agent frameworks преждевременно;
- integrations: внешние travel API должны быть скрыты за provider-интерфейсами и начинаться как mock/stub providers.

Перед технической реализацией должны быть последовательно уточнены требования, пользовательские сценарии, MVP scope, acceptance criteria, доменная модель, архитектурные ограничения и конкретные roadmap-задачи.

## Контроль roadmap

- Проект ведется поэтапно: сначала требования, пользовательские сценарии, MVP scope и acceptance criteria; затем доменная модель и архитектурные ограничения; только после этого техническая реализация.
- Не переопределяй roadmap.
- Не меняй порядок этапов roadmap.
- Не начинай следующий этап roadmap без явного запроса пользователя.
- Не трактуй задачу как разрешение выполнять работу из будущих этапов.
- Работай только внутри явно указанного или очевидно текущего этапа roadmap.
- Перед изменениями определи текущий этап и проверь, что задача относится к нему.
- Не перескакивай к реализации, выбору библиотек, созданию backend/frontend skeleton, интеграциям или инфраструктуре, если текущая задача относится к продуктовой или аналитической проработке.
- Используй технические ориентиры только как контекст и защитные границы, а не как основание для расширения scope.
- Не добавляй артефакты будущего этапа, даже если они кажутся маленькими или полезными.
- Не превращай подготовительную задачу в реализацию продукта.
- Не добавляй реальные LLM/travel API integrations, production infrastructure или UI/backend skeleton, если текущий этап этого не требует.
- Если запрошено обновление roadmap, обновляй только подходящую существующую область roadmap и сохраняй порядок этапов.
- Если подходящей области roadmap нет, перечисли предлагаемую будущую работу в разделе `Рекомендации, не выполнены` финального отчета вместо реализации.

## Контроль scope

- Держи каждое изменение маленьким, атомарным и соответствующим запрошенной задаче.
- Не расширяй scope, если без этого можно выполнить текущую задачу.
- Не выполняй рекомендации в рамках той же задачи.
- Не исправляй соседние проблемы, если они не блокируют задачу.
- Не добавляй новые документы, директории, шаблоны, зависимости или tooling без явного запроса.
- Не создавай автоматически `docs/product/`, `docs/architecture/stage-*`, `docs/product/stage-*` или `docs/decisions/`.
- Если задача требует похожую структуру, сначала используй существующие документы текущего репозитория или укажи предложение в `Рекомендации, не выполнены`.
- Если обнаружена полезная будущая работа, запиши ее только в `Рекомендации, не выполнены`.
- Не добавляй реальные интеграции с travel API до стабилизации domain model и provider-интерфейсов.
- Не хардкодь детали внешних API, credentials или provider-specific допущения.
- Не трогай unrelated files.

## Контроль ADR

- `docs/decisions/` используется только если эта директория реально существует в текущем репозитории.
- Не предполагается, что `docs/decisions/` существует.
- Если `docs/decisions/` отсутствует, не ссылайся на ADR как на обязательный источник.
- Перед изменением архитектуры, публичных контрактов, зависимостей, структуры модулей или provider-интерфейсов проверь ADR только при фактическом наличии `docs/decisions/`.
- Если ADR существуют в текущем репозитории, они имеют приоритет над общими заметками, README и неформальными комментариями.
- Не нарушай существующий ADR без явного запроса пользователя.
- Не создавай ADR автоматически.
- Если задача требует решения, которое не покрыто существующими ADR, укажи необходимость ADR в `Рекомендации, не выполнены`, если создание ADR не входит в текущую задачу.
- Если задача конфликтует с ADR, остановись на безопасной части работы, опиши конфликт в `Открытые вопросы` и не выполняй спорное изменение.

## Контроль архитектуры

- Держи domain logic независимой от Ktor, Next.js, PostgreSQL, Redis и конкретных LLM providers.
- Держи Ktor routing тонким слоем и делегируй поведение в application/domain use cases.
- Держи LLM orchestration независимой от провайдера через `LlmClient`.
- Держи travel search за flight и hotel provider-интерфейсами.
- Предпочитай mock/stub providers, пока MVP domain model и contracts не стабилизированы.

## Контроль документации

- Public contracts и architecture decisions должны быть задокументированы до реализации или вместе с ней.
- Если меняется поведение, архитектура или task workflow, обнови релевантную документацию.
- README и index-документы обновляй только когда меняется навигация, расположение важных файлов, способ запуска или основной workflow.
- Не добавляй ссылки на несуществующие документы, если задача явно не создает эти документы.
- Не дублируй подробное содержание roadmap в README; README должен оставаться навигационным входом.
- Будущая работа должна фиксироваться только в разделе `Рекомендации, не выполнены`, а не реализовываться молча.
- ADR, если они есть, имеют приоритет над неформальными заметками.

## Конфликты и неопределённость

- Если задача, roadmap и ADR конфликтуют, соблюдай ADR и текущий roadmap, а конфликт вынеси в `Открытые вопросы`.
- Если пользователь явно просит нарушить roadmap или ADR, выполни только безопасную часть и уточни риск в финальном отчете.
- Если текущий этап не указан, выведи его из roadmap и затронутых файлов. Если это невозможно сделать уверенно, не начинай потенциально опасную реализацию.
- Если acceptance criteria неоднозначны, выбери минимальное изменение, которое соответствует задаче, и зафиксируй допущение в `Принятые решения`.
- Если непонятно, является ли изменение будущим этапом, считай его будущей работой и добавь только в `Рекомендации, не выполнены`.

## Обязательный формат финального отчета

Каждый ответ по задаче должен завершаться этими разделами:

1. Созданные файлы
2. Изменённые файлы
3. Краткое описание изменений
4. Принятые решения
5. Открытые вопросы
6. Рекомендации, не выполнены

Держи отчет кратким. Если в разделе нет пунктов, напиши `Нет`.
