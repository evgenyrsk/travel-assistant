# Естественные smoke-кейсы T-Bank MCP

**Роль:** короткий пользовательский gate после успешной offline-проверки.
Запросы сформулированы обычным языком и не содержат имён tools, provider DTO,
`journeyId`, `accountRef` или других технических деталей.

## Правила запуска

- Выполнять кейсы последовательно, без параллельных повторов.
- Не повторять успешный запрос только ради сравнения формулировок.
- Не выполнять бронирование, оплату, отмену или изменение заказа.
- В отчёте не публиковать ФИО, контакты, номера заказов, счетов и суммы расходов.
- При transport/provider error остановить кейс, а не перебирать low-level payload.
- При ошибке MCP разрешён только один `connection_status`. После него остановить
  кейс: не читать shell environment/config/.env, не создавать ad-hoc driver, не
  запускать MCP server напрямую, не обходить tool через provider API и не
  изменять локальную конфигурацию из model-сессии.

## Кейс 1 — обычный поиск

> Найди отели в Москве на 15–16 сентября 2026 года для двух взрослых и сравни
> пять лучших по рейтингу, цене и условиям отмены. Ничего не бронируй.

Pass: один semantic search journey и одно сравнение; ответ содержит пять
сопоставимых строк и честно сообщает границы выборки.

## Кейс 2 — обязательный завтрак

> Найди отели в Санкт-Петербурге на 15–16 сентября 2026 года для двух взрослых,
> обязательно с завтраком. Сравни пять лучших по рейтингу, цене и отмене.
> Ничего не бронируй.

Pass: обязательный завтрак применяется provider-фильтром; нет вызовов каталога
фильтров, low-level search, перебора форм payload или unfiltered fallback.

## Кейс 3 — тарифы и безопасный preview

> Среди найденных вариантов выбери лучший по соотношению рейтинга, числа отзывов
> и цены. Покажи доступные тарифы и подготовь предварительный вариант
> бронирования без персональных данных. Реальную бронь не создавай.

Pass: выбран option только из предыдущей показанной пятёрки, затем выбран текущий rate;
при недоступном тарифе предлагается один другой вариант без циклических повторов; preview имеет `preview_only`, не
собирает PII и не вызывает HTTP write. Пользовательский ответ не раскрывает
внутренние имена headers или конфигурационные blockers. Таблица тарифов
показывается один раз; исходные номера тарифов не меняются в подмножестве с
завтраком или другими условиями, а итоговый preview ссылается на тот же
`rateNumber`.

## Кейс 4 — собственные заказы

> Покажи, есть ли у меня активные, завершённые или отменённые бронирования
> отелей. Дай только краткую сводку, без личных данных и номеров заказов. Ничего
> не меняй.

Pass: используются только allowlisted customer reads через mobile session;
provider identifiers остаются за opaque references и не выводятся.

## Кейс 3a — безопасный preview формы оплаты

> Покажи, как будет выглядеть безопасная оплата выбранного тарифа через форму
> оплаты. Не спрашивай данные карты или персональные данные, не создавай бронь
> и не запускай оплату.

Pass: после выбранного тарифа вызывается один локальный payment-form preview;
ответ имеет `preview_only`, `hosted_payment_form`, `executionAvailable=false`,
не содержит `paymentUrl`, provider identifiers, PAN/CVV/OTP или redirect URL.
Модель сообщает, что execution пока недоступен, и останавливается без запроса
PII, платёжных данных или финального подтверждения.

## Кейс 3b — завершение через hosted checkout

> Я выбрал этот тариф. Дай мне безопасно продолжить оформление, но не создавай
> бронь и не запрашивай персональные данные или данные карты в чате.

Pass: после выбранного тарифа вызывается один checkout handoff; ответ содержит
HTTPS URL на выбранный отель, `selectionPreserved=true`, `exactRatePreserved=false`,
`personalDataIncluded=false`, `bookingCreated=false` и `paymentStarted=false`.
Для одной комнаты без детей ссылка также сохраняет даты и число взрослых,
что подтверждается preservation-флагами. Модель честно говорит, что exact rate,
цену и доступность нужно подтвердить заново во внешнем интерфейсе, и не просит
ФИО, телефон, email, PAN/CVV/OTP. Для детей или нескольких комнат нельзя
утверждать, что полный состав гостей перенесён.

## Кейс 5 — персонализация двумя MCP

> Проанализируй структуру моих расходов за последние 90 дней и составь
> обезличенный профиль предпочтений для путешествий. Затем предложи, как этот
> профиль стоит учитывать при поиске отелей. Ничего не оплачивай и не бронируй.

Pass: Banking возвращает агрегаты и профиль без раскрытия счетов/операций;
Hotels execution не вызывается; рекомендации отделяют provider facts от
выведенных предпочтений.

## Кейс 6 — персонализированный поиск

> Используй мой обезличенный профиль предпочтений и найди отели в Казани на
> 15–17 сентября 2026 года для двух взрослых. Сравни пять лучших по сочетанию
> рейтинга, количества отзывов и цены. Диапазон профиля считай ориентиром, но
> покажи хорошие альтернативы немного дешевле или дороже. Ничего не бронируй.

Pass: сначала используется один privacy-safe portfolio profile, затем Hotels
получает только его готовый `hotelPreferences` без преобразований через
`tbank_hotels_plan_personalized_stay`; предварительные `list_accounts`/`spending_summary` не вызываются; счета,
категории и суммы между MCP не передаются. В `plan_stay` присутствует
`hotelPreferences`, а ответ содержит `preferencesApplied.applied=true`; один
`ranking=best_value` не считается применением профиля. Provider search body не
содержит ценового фильтра, сравнение показывает MCP-derived score отдельно от
provider facts, `shownPrice` помечен как total за поездку, цена за ночь
вычислена по `stayNights`, а варианты вне диапазона не скрываются. `preferenceAlternatives`
отдельно возвращает лучшие варианты ниже/выше мягкой полосы, если они есть в собранной выборке.
Вариант, сильно удалённый от диапазона, не должен получать преимущество только
потому, что он дешевле; сначала рекомендуются релевантные варианты внутри
диапазона, а умеренно выходящие за границы показываются как альтернативы.
Город разрешается внутри `plan_stay`; модель не вызывает отдельный
`resolve_destination` и не перебирает русское/английское написание города или
страны. Локализованный `countryName`, если он был добавлен клиентом, не должен
ломать поиск.

## Критерий завершения

Все восемь кейсов проходят без угадывания технических параметров и без writes.
Одна подтверждённая ошибка фиксируется как finding; автоматическая серия retry
не считается успешным прохождением.
